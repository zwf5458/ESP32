日期：2026-11-11

## 1. 结论

ESP32-C5 硬件具备双频 WiFi 6（2.4G + 5G）、BLE 5、802.15.4（Zigbee/Thread）能力。
本文档最初记录的是「固件只用了 2.4GHz」的差距，现已按 P0→P3 逐项补齐：

- **5GHz**：✅ 已实现（P0/P1）—— 扫描、抓包、取消认证、双子、AP 热点均已扩到 5G
  （非 DFS 可承载 AP，DFS 只能做双子/注入），待真机验证；
- **BLE 5**：✅ 已实现（P2）—— 纯被动广播嗅探；C3/C5/C6/S3 开放（NimBLE），
  经典 ESP32 因 Bluedroid 体积与双 app 槽冲突裁剪，S2 无蓝牙硬件；待真机验证；
- **802.15.4**：✅ 已实现（P3）—— 纯被动帧嗅探 + 信道能量扫描；C5/C6 开放，
  其余芯片整页隐藏且 API 返回 501；与 WiFi 2.4G 共用射频，AP 保持在线、抓包为
  分时采样；待真机验证。

下面 §2 保留「改造前」的代码事实作为起点记录，§4 记录各项实际落点。

## 4. 改造清单

### P0：5GHz 扫描 + 抓包（已实现，待真机验证）

目标：C5 上 Sniffer / Airodump 能停驻并跳频 5GHz 信道，抓到 5G 管理帧与数据帧。

- [x] **信道模型**：2.4G（1–14）与 5G（36–165）信道号**不重叠**，因此不引入独立的
      `struct WifiChan`，而是由信道号推导 band（`isBand5G()`）。这样
      `sSniffer.channel` / `sAirodump.currentChannel` / `apChannelActive` 的裸数字语义
      保持不变，`sDeauth.targetChannel` / `sEvilTwin.restoreChannel` 无需改动（P0 不涉及）。
      JSON 侧保留 `channel`（数字），新增 `band`（`2` / `5`）与 `skipDfs`，向后兼容。
- [x] **band 切换**：Arduino `espWiFiStart()` 已在 C5 上自动执行
      `esp_wifi_set_band_mode(WIFI_BAND_MODE_AUTO)`（`WiFiGeneric.cpp:357-360`），
      无需额外调用；`esp_wifi_set_channel(36, WIFI_SECOND_CHAN_NONE)` 的 5G 隐式切 band
      仍列为真机复核项。
- [x] **跳频表**：2.4G `1..13` 与 5G 25 个信道分组循环；
      新增「跳过 DFS」开关（默认开，跳过 52–144），由 `nextHopChannel()` 实现。
- [x] **接口放宽**：`handleSnifferStart` / `handleAirodumpStart` 按信道表校验，
      支持 `channel`（1–14 / 36–165）与可选 `band`（`"24"` / `"5"`，用于跳频起点）；
      非 C5 芯片收到 5G 请求返回 400。
- [x] **后台 UI**：Sniffer / Airodump 的信道下拉按 2.4G / 5G 分组（5G 仅在
      `/api/info` 的 `band5g` 为 true 时显示），新增「跳过 DFS」开关与 5G 驻留提示。
- [x] **提示**：面板标注「5G 驻留时单射频热点会同步切到 5G 或短暂离线」——见 §6 共存风险。
- [x] **编译验证**：6 个 env（esp32 / s2 / s3 / c3 / c5 / c6）全部编译通过；
      `npm test` 39/39。非 C5 芯片的 5G 表与校验在编译期裁掉，2.4G 路径不变。

### P2：BLE 5 嗅探 / 广播扫描

- [x] **依赖**：用 Arduino core 自带的 BLE 库（`BLEDevice` / `BLEScan`），它本身按
      `SOC_BLE_SUPPORTED` 门控、按后端分派：经典 ESP32 = Bluedroid，C3/C5/C6/S3 =
      NimBLE，S2 无蓝牙硬件。无需引入外部依赖。
- [x] **模块**：新增「BLE 扫描」页：广播包（ADV_IND / SCAN_RSP 等）列表，
      字段 MAC / RSSI / 名称 / 广播类型 / 厂商数据摘要 / 广播计数 / 最后出现时间；
      设备数、累计广播数、运行时长与引擎状态如实回显。
- [x] **共存**：AP 保持在线（不中断），默认 50% 扫描占空比（interval 100ms /
      window 50ms）由控制器共存仲裁调度，面板明确提示 AP 吞吐下降。
- [x] **资源回收**：停止时 `BLEDevice::deinit(false)` 拆掉协议栈与控制器、归还射频
      占用（保留 BT 内存以便下次直接重启）；管理任务按需创建，不用 BLE 的部署不占任务栈。
- [x] **API**：`POST /api/ble/start`（body 可选 `duration` 秒，缺省持续）、
      `POST /api/ble/stop`、`GET /api/ble/status`（统计 + 设备列表）、
      `GET /api/ble/devices`（纯数组，面板「导出 JSON」消费）、`POST /api/ble/clear`。
      遥测沿用 `lab_state`（`module="ble"`，只发模块名与 running）。
- [x] **能力裁剪**：门控宏为 `FW_BLE_SUPPORTED = SOC_BLE_SUPPORTED && !FW_BLE_DISABLED`。
      经典 ESP32 的 Bluedroid 比 NimBLE 多约 810KB（实测 1.29MB→2.02MB），与 min_spiffs
      的双 app 槽（三系统引导 `esp_ota_set_boot_partition` 依赖）在 4MB Flash 上无法共存，
      故 `platformio.ini` 的 `[env:esp32]` 用 `-DFW_BLE_DISABLED` 裁剪，其余 4 款正常开放。

实现落点（`firmware/src/main.cpp` / `firmware/data/admin.html`）：

| 项 | 位置 |
|---|---|
| 能力门控 | `FW_BLE_SUPPORTED`（main.cpp 顶部）+ `platformio.ini` 的 `-DFW_BLE_DISABLED` |
| 状态与设备表 | `BleState` / `BleDeviceEntry`（24 条上限，满则淘汰最久未出现） |
| 逐条广播回调 | `BleAdvCallbacks::onResult` → `bleStoreAdv()`（临界区内只做定长拷贝，不拼 String） |
| 生命周期 | `bleTaskFunc` 状态机 IDLE→STARTING→RUNNING→STOPPING，所有协议栈调用串行 |
| 持续模式 | 10s 切片循环重开（`BLE_SLICE_SEC`），保证 RSSI 新鲜、库内部结果表不膨胀 |
| API | `handleBleStart/Stop/Status/Devices/Clear`（无 BLE 芯片统一返回 501） |
| UI | `renderBle()` / `bleUpdate()` / `blePaintRows()`；无 BLE 的芯片整页隐藏 |

验收：能稳定列出周边 BLE 设备；AP 仍可用（可接受吞吐下降）；停止后资源回收。

> 状态：**代码已实现，待真机验证**（需 C3/C5/C6/S3 实机确认扫描稳定性、AP 共存吞吐、
> `deinit` 后再次启动；经典 ESP32 与 S2 无 BLE 页属预期行为）。

### P3：802.15.4（Thread / Zigbee）嗅探

- [x] **依赖**：直接调用 ESP-IDF `esp_ieee802154` API（不依赖 Arduino 包装）。C5/C6 框架包
      （`framework-arduinoespressif32-esp32c5-libs` / `-esp32c6-libs`）的 sdkconfig 均为
      `CONFIG_IEEE802154_ENABLED=y`，静态库 `libieee802154.a` / `libesp_hal_ieee802154.a`
      随框架编入，无需改 `platformio.ini`；链接实测约 +11.6KB Flash / +5.2KB RAM。
- [x] **模块**：新增「802.15.4 扫描」页，两种模式——
      **帧嗅探**（固定信道或 11-26 跳频，驻留 500ms/信道）：解析帧类型（Beacon / Data /
      ACK / MAC 命令）、PAN ID、源短地址/扩展地址、RSSI、LQI、末帧类型，按 PAN 与设备聚合；
      **能量扫描**（11-26 逐信道 `energy_detect`，320 symbol ≈ 5.12ms）：绘制信道占用条，
      标红与 AP 当前信道重叠的频道。
- [x] **纯被动**：`esp_ieee802154_set_promiscuous(true)`，只接收、不发送、不自动 ACK、
      不做任何注入；帧解析在 ISR 回调内完成整数解析，临界区内只做定长拷贝/数值更新，
      不碰 `String` / 日志 / 堆，随后调用 `esp_ieee802154_receive_handle_done()` 归还缓冲。
- [x] **共存**：802.15.4 与 WiFi 2.4G 共用射频前端，框架已开
      `CONFIG_ESP_COEX_SW_COEXIST_ENABLE` 做分时仲裁。**不停 AP**（后台 UI 就跑在 AP 上，
      停 AP 等于切断控制通道），改为「分时采样」：面板如实提示抓包非全量、与 AP 信道重叠时
      丢帧明显增多，并建议把 802.15.4 信道与 AP 错开。
- [x] **API**：`POST /api/ieee802154/start`（body 可选 `mode`=frames/energy、`channel`
      =0 跳频或 11-26、`duration` 秒）、`POST /api/ieee802154/stop`、
      `GET /api/ieee802154/status`（统计 + PAN/设备表 + 能量值）、
      `GET /api/ieee802154/frames`（面板「导出 JSON」消费）、`POST /api/ieee802154/clear`。
      遥测复用 `lab_state`（`module="ieee802154"`），不新增事件类型。
- [x] **能力裁剪**：门控宏
      `FW_IEEE802154_SUPPORTED = SOC_IEEE802154_SUPPORTED && defined(CONFIG_IEEE802154_ENABLED) && !FW_IEEE802154_DISABLED`。
      路由在所有芯片一致注册，无该射频的芯片返回 501；后台按 `/api/info.ieee802154.supported`
      隐藏整页并拒绝直接进入该 hash。6 芯片源码不分叉。

实现落点（`firmware/src/main.cpp` / `firmware/data/admin.html`）：

| 项 | 位置 |
|---|---|
| 能力门控 | `FW_IEEE802154_SUPPORTED`（main.cpp 顶部，靠框架 sdkconfig 判定） |
| 状态与聚合表 | `I154State` / `I154PanEntry` / `I154DevEntry`（PAN 12 条、设备 20 条，满则淘汰最久未出现） |
| 帧解析（ISR） | `esp_ieee802154_receive_done`（`IRAM_ATTR`）→ `i154HandleFrame()`；FCS 已被硬件替换为 RSSI/LQI，`frame[0]` 为长度 |
| 能量检测（ISR） | `esp_ieee802154_energy_detect_done`（`IRAM_ATTR`）→ 记录 dBm，由任务侧轮询完成标志 |
| 生命周期 | `i154TaskFunc` 状态机 IDLE→STARTING→RUNNING→STOPPING；`enable` / `set_channel` / `receive` / `energy_detect` / `disable` 全在任务内串行 |

| UI | `renderI154()` / `i154Update()` / `i154PaintPans()` / `i154PaintDevs()` / `i154EdBars()`；无射频芯片整页隐藏 |

验收：能观察到真实 Zigbee/Thread 设备的帧计数增长与 PAN/源地址；能量扫描读数随周边占用变化；
AP 在全过程中保持在线；停止后射频归还，可再次启动。

> 状态：**代码已实现，待真机验证**（需 ESP32-C5 / C6 实机确认帧解析正确性、能量检测读值、

## 5. 关键设计决策

1. **信道号即 band**：2.4G（1–14）与 5G（36–165）信道号不重叠，band 可由信道号推导，
   不必额外维护 `(band, channel)` 二元组，也就不会出现「跳频后 band 漂移」。
   API 的可选 `band` 字段只用于决定跳频起点频段（`"24"` / `"5"`）。
2. **NVS 兼容（P1）**：P0 不改 NVS（AP 配置仍为 2.4G 1–13）；P1 做 5G AP 时再新增
   `band` 与 `channel5`（uchar），旧设备升级后默认为 2.4G，不改变现有行为。
3. **API 兼容**：所有既有的 `channel` 数字语义不变（2.4G）；新增可选 `band`；
   老前端不发 `band` 时，停驻模式按 `channel` 数值判断，跳频模式沿用当前信道所在频段。
4. **能力门控**：所有 5G 分支用 `#if SOC_WIFI_SUPPORT_5G` 包裹，
   非 C5 芯片编译后代码路径不变，保证 6 芯片镜像构建不分叉。
5. **UI 不新增页面**：5G 复用现有页面的信道选择；BLE / 802.15.4 各新增一页（P2/P3）。

## 6. 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `softAP` 在 5G/DFS 信道不稳定 | P1 无法交付 | 先做 P0（只收不发），DFS 信道默认跳过；只开放非 DFS 段 |
| WiFi / BLE / 802.15.4 共用射频 | 同时开启互相降速、丢包 | 分时共存 + 面板显式提示；802.15.4 采用「保持 AP 在线 + 分时采样」，不承诺并发性能 |
| 5G 驻留导致 AP 掉线 | 后台失联，只能靠串口 | 抓包期间允许 AP 短暂离线；串口控制台始终可用；UI 提示 |
| `esp_wifi_set_channel` 的 band 语义与 IDF 版本绑定 | 换 IDF/平台后回归 | 固定平台版本；把「band 确认」写成启动自检并打日志 |
| 5G 设备覆盖范围短 | 教学演示距离受限 | 文档写明适用场景（近距离、同房间） |
| 抓包/注入的法律边界 | 合规风险 | 5G 目标取消认证需显式确认；文档重申授权边界 |

## 7. 验证计划与前置依赖

- **真机**：一块 ESP32-C5（16MB Flash / 8MB PSRAM，双 Type-C，UART 口刷写）；
- **对端**：一台支持 5GHz 的路由器 + 一部 5G 手机（P0/P1）；一个 BLE 手环/耳机（P2）；
  一个 Zigbee 设备（如智能插座）或 Thread 边界路由器（P3）；
- **回归**：其余 5 颗芯片需重跑 `npm test` 与基础 AP/抓包冒烟，确认 2.4G 路径未变；
- **编译验证（P0 已完成）**：esp32 / s2 / s3 / c3 / c5 / c6 六个 env 全部编译通过，
  `npm test` 39/39；C5 真机抓包仍需板子到货后执行；
- **每阶段独立出镜像**：按 `sh tools/build-firmware.sh <版本>` 注册，不与其他阶段混提。

## 8. 排期建议

| 顺序 | 内容 | 依赖 | 建议 |
|---|---|---|---|
| 0 | v1.1.0 C5 真机首刷（随机口令/热点/后台/2.4G 三模块） | 无 | **先做**，是后续一切验证的基线 |
| 1 | P0 5G 扫描 + 抓包 | 首刷通过 | 优先，改动集中、只收不发、风险最低 |
| 2 | P1 5G AP + 取消认证/双子 | P0 的 band 模型 + `softAP` 5G 实测 | 需先确认 DFS 行为 |
| 3 | P2 BLE 5 嗅探 | 射频共存方案 | ✅ 已完成（待真机）；经典 ESP32 因 Bluedroid 体积裁剪 |
| 4 | P3 802.15.4 嗅探 | IDF 802.15.4 API 可用性确认 | ✅ 已完成（待真机）；与 WiFi 共存分时采样，不停 AP |
| 5 | P4 设备识别与指纹 | P2/P3 已收数据 + 体积余量 | 🟡 P4-0/P4-1 已完成（待真机），见 [P4 roadmap](./2026-11-12-p4-device-identification-roadmap.md) |

> 不建议把 5G 与 BLE/802.15.4 合并成一次改动：三者都要改射频调度与 UI，
> 混在一起会让「到底是哪一项导致 AP 掉线/丢包」无法定位。

## 9. 明确不做的部分

- **5GHz 主动注入之外的花样**（如 5G 下的 Karma 自动应答）：C5 raw TX 在 5G 上的
  SDK 支持度未验证，且与现有「显式启停 + 状态如实回显」的边界不符，暂不纳入；
- **BLE 广播注入 / 802.15.4 帧注入**：只做观察与统计，不做伪造；
- **用满 16MB Flash / 启用 8MB PSRAM**：与本次能力无关，单独评估（当前镜像 4MB，
  分区表 `min_spiffs.csv` 自洽）。
